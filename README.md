# Football Decision Prototype (v0)

Текстовый прототип футбольной RPG на украинском. Проверяет одну гипотезу: **интересно ли принимать
решения в отдельных футбольных эпизодах само по себе, без графики, анимации и симуляции поля.**

Если в текстовом виде скучно — концепт не спасут ни пиксель-арт, ни комикс-сцены.

## Запуск

```bash
npm install
npm run dev      # прототип на localhost
npm test         # юнит-тесты движка и проверки контента
npm run sim      # балансный прогон ботами, по умолчанию 1000 матчей на политику
npm run build    # статика в dist/
```

Выкладка — GitHub Pages: пуш в `main` запускает `.github/workflows/pages.yml` (тесты → сборка →
деплой). В репозитории один раз включить Settings → Pages → Source: GitHub Actions.

Экран `/stats` (ссылка есть с итогового экрана) показывает распределение выборов по эпизодам
из локальной телеметрии. Кнопка «Выгрузить логи» отдаёт весь лог решений одним JSON.

Матч воспроизводится по сиду: `?seed=12345` в адресе запустит тот же матч.

## Что где

```
src/engine/     чистая логика без React: бросок, контекст, машина состояний, все константы
src/content/    эпизоды, футболист и ростер — обычный JSON, править можно не глядя в код
src/ui/         экраны: лента, карточка эпизода, бросок, итог, /stats, debug
src/telemetry/  лог решений в localStorage
tools/simulate  балансный прогон
```

Перед матчем — брифинг с условиями (`src/engine/conditions.ts`): суперник из трёх клубов разной
силы, дом/выезд, погода, установка тренера, тонус из истории матчей на этом устройстве. Условия
генерируются по сиду, игрок их не выбирает; каждое обещание брифинга потом появляется строкой
модификатора после броска. Балансный прогон по умолчанию идёт на нейтральных условиях,
`npm run sim -- 600 --random-conditions` проверяет, что условия не ломают разрыв политик.

Пул — 23 эпизода на 10 слотов матча, чтобы второй матч не повторял первый. Фамилии партнёров
и соперников в текстах — плейсхолдеры (`{partner.dat}`, `{them.striker}`), формы падежей лежат
в `src/content/roster.json`: при смене команды в карьере эпизоды переписывать не придётся.

Весь баланс — в `src/engine/balance.ts`. После любой правки этого файла гоняем `npm run sim`.

## Чего в прототипе нет намеренно

Симуляции матча, спрайтов, комикс-сцен, карьеры, трансферов, сезонов, монетизации,
реролла, бэкенда, аккаунтов, звука и мобильной сборки. Любой из этих пунктов, добавленный
«раз уж всё равно делаем», ломает эксперимент.

## Текущие цифры баланса

Прогон на 2000 матчей на политику (`npm run sim -- 2000`):

| политика | результат | тренер | трибуны | голы ср. | badFail |
|---|---|---|---|---|---|
| always_safe | 6.71 | 7.70 | 5.73 | 0.00 | 0.4% |
| always_risky | 6.18 | 4.16 | 8.19 | 0.49 | 18.6% |
| greedy_personal | 6.59 | 4.74 | 8.44 | 0.81 | 15.0% |
| random | 6.97 | 6.10 | 7.83 | 0.40 | 8.3% |

Разрыв лучшей и худшей политики — 12.8% при пороге 15%, доля badFail — 10.6% при коридоре 8–15%.
Осторожная игра нравится тренеру и усыпляет трибуны, рискованная — наоборот; ни одна
из крайностей не выигрывает по сумме. Это и есть условие, при котором игра не превращается
в калькулятор.

Пороги исходов в `balance.ts` отличаются от первоначальной таблицы ТЗ: на исходных числах
доля badFail держалась около 35%, а `always_safe` выигрывал с отрывом 58%. Таблица подбиралась
прогоном, как и предполагал п. 11.

При расширении пула с 10 до 23 эпизодов баланс правился контентом, а не движком: в новых эпизодах
гол на `cost` заменён командным голом, часть «відчайдушно» понижена до «ризиковано», стоимость
дорогих опций подтянута к старым.

**После первого плейтеста (16.09.2026)** изменилась сама механика, и критерии приёмки правились
осознанно:

- «Упевнено» получило планку кубика 4 (`DIE_FLOOR`): единица на надёжном варианте не выпадает,
  катастрофа возможна только через минусы контекста. Разница показывается строкой «надійний хід +N».
- Полоса «вийшло, але…» сужена на 2 у каждой формы риска — 15 на кубике при риске стал чистым
  успехом. 18 пустых cost-исходов («ничего не случилось, +1 тренеру») переписаны так, чтобы
  в каждом был осязаемый плюс.
- Перерыв возвращает 8 сил; варианты на швидкість/корпус стоят на 4 дороже (`optionCost`).
- Слой реплик по ситуации (`flavor.json`): короткая ироничная фраза после исхода, зависящая
  от счёта, минуты, усталости, серии, карточки и доверия тренера.
- Игра стала щедрее: у бота, бьющего из каждого эпизода, 1.2 гола за матч и хвост до 4 —
  критерий по хвосту поднят с 3 до 4. Случайная политика держится на 0.6 гола и 38% матчей с голом.
  Критерий по стамине: медиана до 70-й, 90-й перцентиль до 80-й (редкий сид с пенальти и перерывом
  тянет ноль до 82-й).

**Второй раунд (по логам двух матчей):**

- Скилл виден на фоне кубика: модификатор атрибута считается от 45 шагом 4 (`ATTR_MOD`), стартовый
  коридор 45..65 даёт 0..+5 и никогда не минус; в строке броска показывается значение — «пас (62) +4».
  Пороги сдвинуты на +1. Отрицательный кураж зажат до −2: в логе была спираль «провали тиснуть −3»
  плюс «ноги стали −4», после которой любой риск невозможен.
- 9 эпизодов вместо 10 и квота — минимум 3 оборонительных за матч (`minDefense`, слоты под них
  выбираются заранее). Пул 27: добавлены четыре защитных эпизода (последний защитник, блок удара,
  опека плеймейкера, розыгрыш их углового накоротке).
- Память между матчами: эпизоды двух последних матчей получают вес 0.02 (`recentWeight`). Второй
  матч повторяет первый на ~4%, третий — первые два на ~32% (без памяти ~33% и ~55%); дальше снижает
  только рост пула.
- Условия матча проверены изолированно (600 матчей на условие): соперник, усталость и установка
  тренера работали, погода и форма были косметикой. Дождь и ветер теперь −2, жара ×1.5 к расходу,
  форма — стартовый кураж ±1, который живёт дальше как обычный momentum. Скрипт замера —
  в комментарии к `BALANCE.conditions`.
- Критерий по стамине под 9 эпизодов: медиана до 75-й (до двух последних слотов), p90 до 80-й.

**M1 — карточка персонажа (см. DESIGN.md):**

- Кубик — **2d10** вместо d20: колокол со средним 11, серии 5-5-5-1 редеют вчетверо, скилл +4
  весит больше на фоне разброса. Пороги подобраны заново (`THRESHOLDS`).
- **Катастрофа — по сырым кубикам** (`CATASTROPHE_BAND`: упевнено 2, ризиковано 5, відчайдушно 7),
  скилл и контекст решают только провал/«вийшло, але…»/чисто. До этого рискованный вариант с сильным
  атрибутом доминировал надёжный со слабым (45% чистого при 1% катастрофы против 36%), и беречься
  не было смысла. Планка кубика убрана — полоса катастрофы делает её работу. 20 — всегда чисто.
- Десять атрибутов в трёх группах; добавлены перший дотик, бачення поля, позиція и витривалість
  (снижает расход сил). Опции перетегированы, «відбір» ушёл в позицію/швидкість/корпус.
- Лист персонажа (`#/player`) и чип атрибута с модификатором на каждом варианте: скилл виден до броска.
- Истощение бьёт по цене варианта: −4 за 12 сил, −2 за 6, −1 за 2. Дешёвое решение на нулевых силах
  остаётся рабочим (в логах 8 из 9 решений при силах ≤10 проваливались).
- Кураж симметричный: катастрофа −1, «вийшло, але…» при минусе возвращает +1.

## Открытые вопросы — заполнить после теста на живых людях

Пять человек, по одному матчу минимум, логи собираются кнопкой на итоговом экране.

0. **Ощущаются ли условия матча.** Тестер после матча должен вспомнить хотя бы одно: что был
   выезд, что шёл дождь, что тренер просил тиснути. Если брифинг читают и забывают — условия
   слишком тихие, усиливать модификаторы или реплики.
   > _(заполнить)_

1. **В каких эпизодах распределение выборов оказалось однородным и почему.**
   Смотреть на `/stats`: любая опция больше 55% — повод присмотреться, больше 70% — эпизод
   переписывать, решение в нём мнимое.
   > _(заполнить)_

2. **Жалуются ли тестеры на рандом.**
   Если да — проблема, скорее всего, в подаче броска или в глубине провала, а не в математике.
   Проверять в таком порядке: видно ли модификаторы после броска, не слишком ли дорого
   стоит один `badFail`, и только потом лезть в `balance.ts`.
   > _(заполнить)_

3. **Хотят ли сыграть второй матч без просьбы.**
   > _(заполнить)_

4. **Что они рассказывают о матче своими словами.**
   Сравнивать с автопересказом на итоговом экране: совпадают ли моменты, которые запомнились
   человеку, с теми, которые прототип счёл ключевыми.
   > _(заполнить)_
